# Этап 12b: подтверждённое применение отката

Дата: 27 ноября 2026. Реализована вторая часть 12b в текущем checkout. Публикация и включение на рабочем сервере не выполнялись.

## Подтверждение и границы операции

Для применения нужны оба флага: `RUNOZA_ROLLBACK_PREVIEW=true` и `RUNOZA_ROLLBACK_APPLY=true`. Применение выключено по умолчанию. Свежий успешный preview получает серверное подтверждение, связанное с его ID, пользователем, поколением среды, проектом, desktop target, составом журнала и точным набором путей/версий. Клиент не передаёт произвольное содержимое файлов, пути для записи или расширение полномочий.

Кнопка «Применить откат…» открывает отдельный диалог с путями, полными hashes текущей и возвращаемой версий и обозначением server/desktop workspace. Первоначальный фокус — «Отмена». Отправка происходит только после явного подтверждения. Сетевой повтор сохраняет тот же request ID и тот же подтверждённый набор. Один preview нельзя применить повторно под новым request ID, в том числе после сбоя с неизвестным исходом. Для следующей попытки требуется новое исследование текущих файлов через preview.

Поддерживается только возврат содержимого существующих текстовых UTF-8 файлов, допущенных первой частью 12b. Сохраняются BOM, переводы строк и пустое содержимое. Создание/удаление файлов, бинарные файлы, shell-эффекты, Git, права исходной исторической версии и история чата не возвращаются. Исходные записи изменений не переписываются: факт отката хранится отдельно.

## Проверка и запись

API проверяет live ACL, CSRF через существующий middleware, права редактора workspace, владельца desktop-устройства, актуальный target, срок и точную версию preview. Подтверждение аудируется. Операция, строки файлов и workspace-задание создаются одной транзакцией. Уникальность preview и request ID защищает от дублирования при повторных отправках.

Worker получает отдельный lease операции. Он заново загружает и проверяет все сохранённые bundles и все текущие файлы до первой записи. Если хотя бы один файл недоступен, изменён или перестал поддерживаться, записи всего набора не начинаются. В памяти остаются проверенные исходные байты, а в durable журнале — пути, change IDs и expected/restore hashes. Внутренний fingerprint и содержимое файлов не выдаются через API журнала.

Перед каждой записью повторяются ACL/target/cancellation checks. Сам writer использует `expectedHash` и существующую атомарную замену `installResource`/desktop adapter. Управляемые writers сохраняют общую сериализацию; symlink/root checks остаются в исполнителе. Между preflight и конкретной записью внешний редактор может изменить файл: обнаруженный конфликт останавливает остальные записи и сохраняет уже подтверждённые результаты. Для нескольких файлов нет общей файловой транзакции. Как и раньше, hash + rename не является универсальным OS CAS для всех внешних процессов.

Применение не создаёт новую среду. Проверяются исходное поколение и доступная workspace; неизвестная или закрытая среда не подменяется. Сохраняются пределы preview: 50 записей, 25 путей, 8 MiB чтений. Начало исполнения допускается в течение двух минут после подтверждения; всё применение ограничено 120 секундами и поддерживает AbortSignal.

## Журнал, Stop и потеря worker

Миграция `045_managed_rollback` добавляет `rollback_operations` и `rollback_items`. Для файла сохраняются `planned`, `writing`, `applied`, `failed`, `unknown`, `skipped`, время и код причины. Перед внешней записью durable состояние становится `writing`. `applied` означает полученное и сохранённое подтверждение writer. Если запись могла произойти, но ответ или его сохранение потеряны, статус остаётся `unknown`; следующий файл не выполняется.

Операция различает завершение, отказ без подтверждённых записей, частичный результат, отмену до записи и прерывание worker. Журнал показывает результаты каждого файла; успешная запись не исчезает из него при последующей ошибке. API возвращает последние 50 операций текущего пользователя для запуска. Сохранённый журнал доступен и после выключения флагов, при сохранении доступа к исходной беседе.

«Остановить оставшиеся записи» запрашивает остановку, а не обратную компенсацию. Ожидающая операция завершается без записей. Для выполняющейся worker прекращает новые dispatch и прерывает in-flight операцию; если её исход нельзя подтвердить, он помечается неизвестным. Уже подтверждённые записи не отменяются. Закрытие диалога после подтверждения не останавливает операцию; состояние доступно при повторном открытии review.

При смене worker старый lease больше не может продвинуть журнал. `writing` становится `unknown`, остальные невыполненные элементы — `skipped`; автоматического replay нет. Отдельно обработан сбой между захватом workspace-задания и захватом самой операции: он не оставляет беседу навсегда заблокированной. Завершённые до сбоя записи сохраняют `applied`.

Пока откат ожидает или выполняется, новые agent runs и workspace-действия в этой беседе не принимаются. Уже поставленный следующий запрос остаётся в очереди без превращения в ошибочный input. После частичного/прерванного применения очередь приостанавливается с причиной `ROLLBACK_REVIEW_REQUIRED`; пользователь проверяет файлы и возобновляет её существующим действием. Это предотвращает автоматический запуск следующего writer поверх неизвестного исхода.

## Выпуск и откат реализации

Server и worker должны использовать согласованную версию схемы `045_managed_rollback`. Обычное отключение — `RUNOZA_ROLLBACK_APPLY=false`: новые подтверждения запрещаются, выполняющийся worker останавливается с сохранением известного результата. Это не отменяет уже записанные файлы. Preview можно оставить включённым отдельно.

Обратная миграция удаляет только новые записи журнала отката, сохраняя исходные runs, сообщения, revisions и `code_actions`. Она не возвращает содержимое файлов обратно. Перед downgrade нужно остановить worker, сохранить необходимый журнал и согласовать бинарник со схемой по действующему runbook.
