# Этап 7: ограниченное восстановление текста

Реализовано в рабочем checkout поверх этапов 0–6. Изменения используют существующие PiAgentRuntime, PostgreSQL, SSE и общий web/Electron UI. Публикация и миграция пользовательской установки не выполнялись.

## Поведение

Обычный чат и кодовый агент используют один managed stream. Обрыв потока, `finish_reason=length` и временные ошибки соединения/HTTP допускают не более двух восстановлений за весь run. Ошибки авторизации и остальные постоянные ошибки провайдера не повторяются. Скрытые SDK retries отключены только для запросов, управляемых этим протоколом.

До появления текста и любого tool call разрешён повтор исходного запроса. После появления текста отправляется сохранённый ответ с инструкцией вернуть только недостающий суффикс. В этом запросе отсутствуют объявления инструментов, включая добавленные через payload hook. Неожиданный tool call в продолжении завершает восстановление с `RECOVERY_TOOL_CALL` и не исполняется.

Первоначальный ответ публикуется потоково. Каждое текстовое продолжение буферизуется до завершения попытки: точное повторение всего сохранённого ответа или его окончания удаляется перед публикацией суффикса. Уже показанный текст не переписывается. Для частичного совпадения используется граница не короче 16 UTF-16 единиц и окно 16 384 единицы; семантическое перефразирование или повторение в середине ответа не распознаётся. Общий текст ограничен 2 млн UTF-16 единиц. Это техническая защита от точных дублей, а не гарантия качества содержания модели.

Любой увиденный tool call, включая незавершённый и read-only, запрещает дальнейшее автоматическое восстановление в этом run. Наличие прежних `code_actions` также учитывается. Незавершённый JSON не склеивается, выполненные команды не повторяются. При исчерпании бюджета, отмене или ошибке остаётся сохранённый частичный ответ с причиной остановки. Восстановление после инструментов и перезапуска worker остаётся этапом 11.

## Хранение и бюджет

Каждая попытка получает UUID, порядковый номер, parent ID, тип (`model`, `summary`, `retry`, `continuation`), причину, исход, лимиты контекста/выхода, размер полученного текста и сообщённый провайдером usage. Неизвестный usage хранится как `null`, неизвестный output limit — как provider default. История не содержит prompt, секретов или копии ответа.

Резервирование выполняется транзакционно с блокировкой run и проверкой lease. Ответы, повторы, продолжения и сжатие контекста используют один сохраняемый `generation_calls / max_agent_steps`; число восстановлений сохраняется отдельно. Резервирование считается использованной попыткой даже при отмене до HTTP-запроса. Перезагрузка UI, новая инстанция budget helper и compaction не обнуляют счётчики. Сохраняемый срок допуска новых попыток — 10 минут для чата и час для code run с момента первого резервирования; действующие сигналы отмены и runtime timeout сохранены.

Доступ и отмена проверяются при резервировании и повторно непосредственно перед отправкой после backoff. Завершение run закрывает незавершённые попытки как cancelled/interrupted; поздний lease не может перезаписать чужую попытку. Для summary автоматическое восстановление отключено, но сам вызов входит в общий бюджет. Старые метрики runtime сохранены; источником общего лимита и расходов каждой попытки служит новая история, включая summary и неуспешные запросы.

## API и интерфейс

`GET /api/v1/runs/:id/attempts?offset=…` возвращает до 100 попыток, следующий offset и счётчики. Доступ проверяется до и после чтения через существующий ownRun, ответ имеет `private, no-store`. Snapshot и run events содержат `generation_calls` и `recovery_count`.

В подробностях запуска и полосе статуса доступен блок «Попытки модели». Он показывает общий лимит, причины и исходы, использованные восстановления и отсутствие сведений о токенах. Общий query cache объединяет чтения двух представлений. Перезагрузка, пагинация и «Обновить» только читают историю и не запускают модель. Добавлены русские и английские подписи на существующих Gravity-компонентах.

## Миграция и откат

Append-only миграция `041_generation_attempts` добавляет таблицу `generation_attempts` и четыре поля `chat_runs`: `generation_calls`, `recovery_count`, `generation_tool_seen`, `generation_started_at`. Registry и `SCHEMA_VERSION` согласованы. Старые runs получают нулевые счётчики; исходные сообщения и действия не изменяются. Новых npm-зависимостей нет.

Откат `down` удаляет только новую таблицу и четыре поля, включая накопленную историю попыток. Перед откатом требуется остановить новые workers/API и согласовать версию приложения со схемой. Автоматического перепроигрывания существующих runs при миграции нет.

## Проверки

Целевой backend-прогон прошёл: 12 проверок на одноразовой PostgreSQL, реальном HTTP/SSE fixture и настоящих `executeRun`/PiAgentRuntime. Матрица chat/code покрывает сбой до первого токена, обрыв после текста, output limit, монотонный SSE/transcript и повторное чтение истории. Дополнительно проверены незавершённые tool calls, сбой после исполненной команды, поддельный tool в продолжении, общий лимит, исчерпание двух восстановлений, отмена во время backoff, отзыв membership, summary budget, срок и смена lease.

Unit-проверки дополнительно покрывают точное удаление дублей с Unicode, отсутствие скрытых повторов, неизменность частичного ответа, отсутствие usage и запрет retry при 401. UI-проверки покрывают обе темы и локали, клавиатурное раскрытие, повторное монтирование, общий query cache, пагинацию и ошибку обновления без запуска модели.

Полная регрессия прошла: `npm run check` проверил границы пакетов, Prettier, TypeScript, server/web/desktop builds, **111 unit-тестов**, **164 UI-теста в 26 файлах** и лицензии **781** locked packages. `npm run test:integration` завершился с **175 passed, 6 infrastructure skipped, 0 failed** (181 тест). Пропуски относятся к реальным containers/Open Terminal, workspace PTY/stdio, upstream shared terminal и restart storage. Подтверждены прежние сценарии чата, планов, revisions, файлов, ACL, compaction, scheduler и запрета повторного исполнения после потери ответа executor.

После усиления проверок usage и сохраняемого recovery cap отдельно прошли **12** unit-проверок восстановления, typecheck и форматирование изменённых тестов; backend-регрессия включила уточнённый сценарий с новой инстанцией budget helper. `git diff --check` прошёл.
