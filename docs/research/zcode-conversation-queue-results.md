# Этап 8: серверная очередь следующих запросов

Реализовано в рабочем checkout поверх этапов 0–7. Очередь хранит намерения на следующие ходы беседы отдельно от `chat_runs.status=queued`. Уникальное ограничение одного активного run на беседу сохранено. Пользовательская установка не обновлялась, публикация не выполнялась.

## Сервер и жизненный цикл

Добавлены `ConversationQueuedInput`, таблицы `conversation_queues` и `conversation_queued_inputs`. У пункта есть автор, idempotency key, порядковый номер, revision, текст, вложения/revision references, выбранные model/reasoning/mode/intent/approval/extensions, snapshot конфигурации, причина остановки и ссылка на созданный run. Статусы: `queued`, `needs_attention`, `claimed`, `cancelled`. У беседы сохраняются пауза, причина, revision и ожидаемая граница истории. Одновременно допускается не более 100 ожидающих пунктов.

Добавление возвращает ACK после commit. Повтор одного ключа и исходного payload возвращает уже принятый пункт, включая его текущее состояние после редактирования или запуска. Другой payload с тем же ключом вызывает `IDEMPOTENCY_CONFLICT`. Редактирование и удаление требуют ожидаемую revision; после claim менять пункт нельзя. Удаление логическое и сохраняет историю приёма. Редактировать может автор с актуальным правом записи. Пользователи с правом записи в общую беседу могут приостанавливать очередь и удалять ожидающие пункты, включая заблокированный запрос автора, потерявшего доступ; переписывать запрос под чужой identity нельзя.

Валидация добавления и редактирования переиспользует `createRun` в SQL savepoint. Временный run имеет неактивный статус и все временные сообщения, ссылки и изменения head откатываются до ACK; ни job, ни запрос модели не создаются. Это позволяет применять существующие ограничения контекста, references, attachments, моделей, режима планирования, устройств, approvals и расширений без второй упрощённой версии send validation. Preview пропускает только ограничения занятости/параллельных runs, которые обязательно применяются при claim.

Worker проверяет готовые беседы в существующем dispatch loop, примерно раз в секунду. После завершения предыдущего run он берёт первый ожидающий пункт, повторно проверяет автора, ACL, target, доступность устройства и выбранную конфигурацию. Создание нового run, его сообщений и связь с пунктом, изменение статуса пункта и ожидаемого head происходят в одной транзакции. Два workers или клиента не могут создать два run для одного пункта. Лимит параллельных runs откладывает claim, не теряя принятый запрос. Ручная отправка не обгоняет работающую очередь; существующий `RUN_ACTIVE` остаётся действующим.

Snapshot включает target IDs, режим, approvals, загруженные версии skills, MCP IDs и fingerprint конфигурации модели/расширений/инструкций. При изменении модели, выбранной версии, расширений, target или ветки пункт получает `needs_attention`, очередь приостанавливается, временные записи откатываются. Скрытой подстановки модели или рабочей папки нет. References и вложения проверяются снова при claim; недоступный источник не исчезает из запроса молча. Связь claimed run с target дополнительно проверяется перед генерацией. Реально использованные reasoning, instructions и extension manifest сохраняются существующим run snapshot.

Ручная остановка текущего run сначала ставит очередь на паузу. Failed/cancelled и неизвестный исход действия также сохраняют паузу при завершении. Перед claim также проверяется терминальный исход предыдущего run: это закрывает гонку, когда событие завершения ещё не видело первую незакоммиченную строку очереди. `acknowledged_head_id` фиксирует только уже завершённый run, наблюдавшийся при явном возобновлении; нажатие Resume во время работы не подтверждает её будущую ошибку. Возобновление явно подтверждает текущую границу беседы и требует актуальную revision; при `needs_attention` сначала нужно исправить или удалить проблемный пункт. Изменение текста с «Сохранить и перепроверить» обновляет snapshot после повторной валидации. Опция сохранения с настройками композера позволяет явно заменить модель и выбранные расширения.

После сбоя между commit claim и отправкой job существующий dispatcher находит queued run и доставляет его через pg-boss. После сбоя уже работающего worker сохраняется прежний запрет replay: run завершается `WORKER_INTERRUPTED`, очередь приостанавливается. Команды не исполняются повторно ради продвижения очереди. Автоматический повтор неизвестного действия, `Send now` с принудительным прерыванием и DnD в эту поставку не входят.

## API

Все маршруты находятся под `/api/v1/conversations/:id/queue` и используют существующую identity/CSRF инфраструктуру:

- `GET ?offset=…` — состояние и история, до 100 записей; ожидающие сначала по FIFO, затем история от новых к старым.
- `POST` — добавить текст и выбранные параметры с `requestId`.
- `GET /requests/:requestId` — сверить приём собственного запроса после потерянного ACK.
- `PATCH /:itemId` — изменить с `{revision, input}`.
- `DELETE /:itemId` — удалить с `{revision}`.
- `PATCH` — установить `{revision, paused}`.

Чтение проверяет доступ до и после запроса и возвращает `private, no-store`. Изменения сериализуются с run creation через существующие user/conversation locks. GET не отправляет модельные запросы. `/compaction`, retry старого сообщения и принятие плана сохраняют отдельные существующие действия; они не превращаются неявно в пункты очереди.

## Интерфейс и черновики

В общем web/Electron composer при активном run доступны отдельные «Добавить следующим» и «Остановить». Enter добавляет следующий обычный запрос; команда сжатия сохраняет прежнюю семантику. Во время ожидания ACK можно продолжать ввод, а Stop остаётся доступным. После ACK медленное обновление истории не блокирует отправку следующего draft. При наличии ожидающих пунктов новый текст добавляется к очереди, включая очередь на паузе.

ACK очищает только отправленные версии полей исходного draft scope: текст, references, вложения, skills и project search. Новый текст, повторная запись идентичного текста, изменённые вложения и draft другой беседы сохраняются. Неопределённый приём показан отдельно; «Проверить приём» читает запись по ключу, а «Повторить ту же отправку» сначала сверяет ключ и повторяет исходный неизменный payload. Для нового draft не создаётся повтор старого запроса.

Панель очереди показывает принятый текст, порядок, состояние, причины, модель/target, выбранные настройки, связь с run, изменение/удаление и паузу/возобновление. История читается с пагинацией и обновляется примерно раз в 1,5 секунды. Claim уведомляет ChatWorkspace о новом run и подключает существующий SSE. Реализованы EN/RU подписи и существующие Gravity-компоненты. Навигация и повторное чтение очереди не запускают модель.

## Миграция и откат

Append-only миграция `042_conversation_queue` добавляет две таблицы и индексы. Registry и `SCHEMA_VERSION` согласованы. Существующие беседы/сообщения/runs не переписываются; без принятых пунктов исполнение сохраняет прежнее поведение. Новых зависимостей нет. Worker получает существующий storage handle для повторной проверки revision references.

`down` удаляет очередь и её историю, но не уже созданные runs и сообщения. Перед откатом следует остановить API/workers и согласовать версию приложения со схемой; ожидающие намерения будут утрачены при удалении таблиц. Миграционный round-trip проверяется на одноразовой базе.
