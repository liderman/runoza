# Этап 10: ограниченный batch независимых чтений

Реализован `read_batch` поверх существующего PiAgentRuntime. Глобальный режим Pi остаётся `sequential`; выполнение shell, файловых изменений, живых MCP calls и approvals сохраняет прежний порядок. Новых зависимостей и миграций нет, схема остаётся 042.

## Почему отдельный инструмент

Проверен установленный `@earendil-works/pi-agent-core` 1.5.2: `toolExecution: "sequential"` делает последовательным весь batch модели; альтернативный режим запускает разрешённые calls через `Promise.all`. Per-tool `executionMode: "sequential"` также сериализует весь набор. Контракта для пула с лимитом и блокировкой отдельных ресурсов нет. Поэтому выбран предусмотренный планом ограниченный batch-tool. Pi не форкается, `node_modules` не изменяется, глобальный parallel mode не включается.

Каждый дочерний вызов проходит публичный `runToolCall` Pi: валидируются его собственные arguments и schema. Выполняется уже обёрнутый runtime-инструмент, поэтому остаются проверки capability/intent, текущих прав, бюджета, loop guard, ограничения результата и сохранение большого вывода. В provider history попадает один корректный результат на внешний call `read_batch`; внутри результата сохраняются отдельные ID и исход каждого пункта. Вложенные calls не добавляются как непарные assistant/tool messages.

## Серверный список операций

| Tool            | Данные                                                     | Ключ ресурса внутри текущего run | Предел на ресурс |
| --------------- | ---------------------------------------------------------- | -------------------------------- | ---------------: |
| `history_read`  | Страница ранее сохранённого результата в этой беседе       | action ID                        |                1 |
| `skills_search` | Метаданные доступных навыков                               | каталог навыков текущего scope   |                1 |
| `mcp_search`    | Метаданные разрешённых инструментов из локального каталога | каталог MCP текущего scope       |                1 |
| `mcp_schema`    | Кэшированная схема разрешённого инструмента                | connection ID                    |                1 |

Descriptors задаются кодом сервера: `effect=read`, cooperative cancellation и фиксированный лимит. Строки ключей локальны для одного run/actor; между пользователями нет общего cache или scheduler. Ни пользовательский текст, ни имя инструмента в MCP schema, ни `readOnlyHint` не расширяют список.

`mcp_list`, `mcp_call`, shell, workspace reads/writes, scratch writes, skill resources и рекурсивный batch в список не входят. Batch не открывает MCP-сессии и не занимает workspace lease. В плановом режиме он допустим только с теми же разрешёнными дочерними чтениями.

## Ограничения, отмена и частичный сбой

В группе 1–8 пунктов со стабильными уникальными ID; одновременно выполняются не более 3 разрешённых операций. Чтения одного ресурса сериализуются. Зависимости между пунктами не поддерживаются: аргументы должны быть известны заранее. Для действий, зависящих от содержимого ответа, модель должна сначала изучить результаты и затем сформировать следующий вызов. Обычный последовательный Pi loop не запускает следующий writer, пока batch полностью не завершён.

Каждый child повторно проверяет доступ при входе в инструмент; batch дополнительно проверяет scope перед запуском и после результата. Отзыв доступа не позволяет вернуть вновь прочитанные данные. Неизвестная/запрещённая операция, повторяющийся ID или oversized batch отклоняются до начала работы. Ошибка schema конкретного child и обычный `NOT_FOUND` возвращаются как частичный сбой с сохранением независимых успешных результатов.

Stop прекращает выдачу новых пунктов. Уже отправленные DB-чтения завершаются: их драйвер не предоставляет этому пути гарантированную отмену отдельного SQL-запроса. Scheduler дожидается завершения in-flight операций; отменённые результаты не передаются модели как успех. Уже завершённые результаты сохраняют свой исход. Следующее действие не обгоняет оставшиеся чтения.

Parent и каждый реально вызванный child входят в прежний общий бюджет tool calls. Агрегатор не сбрасывает loop guard дочерних операций: его JSON содержит timestamps и не должен маскировать повтор одинаковой ошибки. Bookkeeping и запись состояния guard сериализованы. Тест проверяет остановку на пятом одинаковом failure в отдельных batch-вызовах.

## Журнал и интерфейс

В начале группы создаётся `code_actions` со статусом `running`, который сразу попадает в transcript. В versioned JSON результата сохраняются ID, tool, queued/running/completed/failed/cancelled, начало, окончание, результат и ссылка на отдельный action каждого child. Обновления parent сериализуются и сверяют lease. Обычные actions дочерних инструментов также остаются в истории. Существующий `runEvent` блокирует run row и сохраняет SSE sequence/parts без потерянных событий.

В Gravity-карточке EN/RU показаны состояния и настоящие timestamps; строки сохраняют порядок исходного запроса, даже когда чтения заканчиваются в другом порядке. Полный результат и ошибки доступны в раскрываемых подробностях. Если parent завершён/прерван, а записанный child остался queued/running, UI явно показывает неподтверждённое прерывание. Тот же компонент используется для замороженных карточек истории.

Журнал — свидетельство выполнения, а не механизм автоматического возобновления после падения worker. Replay остаётся `never`. Durable model boundaries и восстановление после инструментов относятся к этапу 11.

## Измерения и включение

Контролируемая fixture: восемь независимых сохранённых страниц, задержка I/O 30 мс на каждую, три повтора с одинаковыми данными. Медиана: **253 мс** с одним слотом и **94 мс** с тремя. Это проверка механизма планирования, не оценка latency production.

Отдельный замер полного runtime использует настоящий Pi, локальный HTTP fixture provider и PostgreSQL, восемь страниц, следующую scratch-file запись, две модельные генерации, live ACL, action journal и SSE. Три повтора с чередованием порядка режимов дали:

| Режим                  | Повтор 1 | Повтор 2 | Повтор 3 | Медиана |
| ---------------------- | -------: | -------: | -------: | ------: |
| Последовательные calls |   506 мс |   812 мс |   638 мс |  638 мс |
| Ограниченный batch     |   537 мс |   586 мс |   679 мс |  586 мс |

Медиана ниже примерно на 8%, но результаты существенно перекрываются: надёжного выигрыша для default-on по этим трём локальным повторам не установлено. Цена дополнительного parent journal и live authorization учтена. Поэтому оптимизация оставлена opt-in, как требует критерий этапа 10. Для реального I/O с большой задержкой есть потенциал, показанный контролируемой fixture, но это не обещание ускорения production.

По умолчанию функция **выключена**. Для пилота:

```dotenv
RUNOZA_READ_BATCH=true
```

Флаг передаётся процессам API и scheduler worker; он добавлен в обе Compose-конфигурации и `.env.example`. `coding_config.readBatch` сохраняется при создании run. Старые runs и runs без этого поля продолжают прежний последовательный путь. Возврат к `false` отключает batch для новых runs; история результатов остаётся читаемой. Настройки реальной пользовательской установки в рамках этой работы не менялись.

Данные замеров: игнорируемые `work/zcode/stage10-benchmark.json` и `stage10-runtime-benchmark.json`. Тайминги диагностические, без flaky assertions на миллисекунды. Для включения по умолчанию нужен выигрыш на полном рабочем сценарии, а не только на искусственной задержке.
