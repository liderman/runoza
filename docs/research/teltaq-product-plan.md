# Product plan and implementation brief

**Decision proposed · 23 November 2026.** Start with two changes people can use in their current chats: open the exact passage behind an answer, and answer a tool's question where the tool is running. Next, make it easy to compare models and reuse a successful setup. Build scheduled reports and structured data analysis on those foundations.

The research covers Teltaq's public beta gallery, product pages and worked examples. Its authenticated app, paid plans, accessibility and response times were not independently tested. The baseline below is the Runóza source at `300e1f9`. Screen flows, interfaces, limits and release targets below are proposals for Runóza. [Teltaq product map](https://www.teltaq.com/) · [Interface gallery](https://www.teltaq.com/screenshots)

## What is already in the product

| Area | Reuse | Gap worth closing |
| --- | --- | --- |
| Chat | Streaming, ordered message parts, per-run usage, branching and a model picker with capabilities and reference rates | A reader can switch answers, but cannot compare two models on identical input in one operation. |
| Projects | Membership, file upload, proxied S3 downloads and explicit attachments | Attaching a document and searching a set of documents are different intentions. Users need to see which sources were searched and verify a passage. |
| Extensions | Internal catalog, versioned skills, pinning, slash invocation, remote and local MCP | An agent configuration is hard to reuse. A permission card authorizes an action but cannot collect a missing date or selection for a running tool. |
| Tasks | Manual and scheduled jobs, policies for missed/overlapping runs, history, unread results and conversation links | Repeated runs accumulate conversation context. A person reviewing a weekly result needs the output, its inputs and what changed. |

Baseline references: [chat](../chat.md), [files and project rights](../files-and-projects.md), [extensions](../extensions-guide.md), [schedules](../schedules.md), [previous model comparison proposal](cherry-studio-ux.md), [ordered message rendering](../design/message-parts.md).

## Delivery order

| Milestone | Deliverable and dependency | Exit decision |
| --- | --- | --- |
| 1. Everyday chat | A. Document sources and B. Tool questions. Independent work. First build the text search and remote MCP form vertical slices. | A reader locates the supporting passage. The sender answers a missing field and the same tool call completes. |
| 2. Model choice | C. Compare two answers. Start with ordinary text turns. | Closing, reopening and continuing from either result preserves history and usage. |
| 3. Reusable work | D. Versioned assistant presets and E. Evaluation cases. E can start with fixtures during milestone 1. | A project editor can test a new assistant version and identify a regression before sharing it. |
| 4. Repeated work | F. Form-driven tasks, review steps and result history. Uses D and the existing scheduler. | One team can run the same brief manually or weekly and inspect the change between two outputs. |
| 5. Evidence-led additions | G. Questions over CSV after A and the evaluation harness. H. Automatic model selection after C and E, subject to a routing benchmark. | Ship G when numbers are reproducible. Enable H when it beats a fixed-model baseline for the installation's chosen objective. |

Each letter is independently flaggable. Keep interaction inside the feature it extends. The sidebar gains **zero** new permanent destinations in this plan.

## Implementation status

Milestone 1 implements project search across TXT, Markdown and text-layer PDFs, named collections, page citations, and form elicitation over HTTP and both stdio brokers. See the [project files guide](../files-and-projects.md) and [extension guide](../extensions-guide.md).

The bilingual retrieval fixture found the expected passage in the top five for all 36 answerable questions. Four unsupported questions produced no results. Browser and Electron checks covered source navigation and a date question in both themes. The release checks cover PDF page provenance, recovery of an expired indexing lease, collection permissions and deletion, plus two questions within a single stdio call. A moderated five-person usability study remains a separate product validation activity. Milestones 2–5 remain planned.

## A. Project knowledge with verifiable citations

**User journey.** In Project → Files, select files and choose **Make searchable**. Show per-file states *Indexing*, *Ready*, *Text unavailable* and *Retry*. In chat, **+ → Search project files** selects a collection and adds a removable chip above the draft. **Attach file** continues to mean “include this file in this message”. Name the selected collection before sending. An answer such as “Claims close after 30 days [1]” opens the evidence beside the conversation: filename, version, PDF page or text heading, highlighted passage and adjacent context. Opening and closing the source preserves reading position. If nothing supports the answer, say so once at the answer.

**Implementation.** Start with TXT/Markdown and searchable PDFs. An isolated, resource-limited extraction job reads via the existing storage adapter. Key the index by scoped file ID, content digest and parser version. Store ordered passages, page/heading offsets and a PostgreSQL full-text index. Use language-aware EN/RU search and an exact identifier path. Scope before ranking and recheck membership when assembling the prompt and opening evidence. Give the model bounded excerpts and opaque source IDs. Only IDs from that run resolve to citations. Persist the source map with the message, including through forks. On file deletion/revocation remove searchable content and redact unavailable previews, including cached snippets. Existing answer text follows the current project deletion policy.

**Rollout and acceptance.** Ship lexical search first. On a fixture of 40 bilingual questions targeting policy clauses, identifiers and unanswerable questions, target the expected passage in the top five for at least 85% of answerable cases. Reject every invented source link. Test a scanned PDF, interrupted indexing, two identically named files, revoked access and a file replaced after the answer. Offer hybrid retrieval only if it improves the missed cases sufficiently to justify an optional embedding dependency. Agent-directed follow-up searches can then reuse the same index and citation map. ## B. Let an MCP tool ask a question in place

**User journey.** A calendar tool needs a date. Its running card expands in the transcript with the server name, the question, a date field and **Send answer**. A secondary action declines and a dismiss action cancels. Validation stays by the field. The sidebar says **Needs your input** and opens the relevant message. After submission the card collapses and the original run continues. A request for information and permission to perform the resulting action remain distinct decisions, including in the conversation's Full access mode.

**Implementation.** Add MCP form elicitation to the negotiated HTTP client, then both stdio brokers. Deliver a private, typed input request keyed by run, tool call, session and MCP request ID. Extend the ordered activity renderer and SSE snapshots. Keep a live handle to the original call, a short configurable deadline, and an atomic, idempotent response endpoint. Only the initiating user with current rights may see or answer the fields. Shared history contains a status and the normal tool result. Retain form answers only as long as needed for delivery. Validate the negotiated schema subset on both sides. Advertise support by transport only after its tests pass. A disconnected tab can resume while the tool session is alive. Session loss expires the request and produces a tool result with the outcome known so far.

**Acceptance.** Cover two questions within one call, double submit from two tabs, decline, timeout, revoked membership, Stop and worker restart. A second project member cannot read the form or win the response race. The tool is invoked once. Unattended jobs return an explicit “interactive input unavailable” result to the agent. The author can collect required values in the task form or put a review before the tool step. A saved review cannot revive an expired MCP session. Form mode excludes credentials. Defer URL mode until trusted-host display, explicit external opening and desktop return flow can be tested together. ## C. Compare answers and keep the better conversation

**User journey.** From the model picker choose **Compare two models**, or from an existing question choose **Compare with another model**. Show the provider of each candidate and how many new requests will be sent. Identify both destinations before sending the same project context to two providers, and enforce any configured destination restrictions for each. Reuse an existing answer only when its input snapshot matches. Wide screens show two labeled columns. Narrow screens show tabs with independent status. Each answer streams, stops and retries separately. **Continue with this answer** selects the branch and its model. The other answer stays available at the question. The ordinary send action retains its current behavior.

**Implementation.** The database currently enforces one active chat run per conversation. Preserve that invariant: create one comparison parent holding the conversation slot, with two independently leased candidate records, a shared immutable input snapshot and separate stream cursors. Reserve two user generation slots atomically for two fresh candidates. One fresh candidate consumes one slot. Use sibling assistant messages under the same user question, set the active head with an expected-head check and block a concurrent ordinary send until the comparison is resolved or closed. Store actual provider usage per candidate and snapshot reference rates if present. Show unavailable costs as unknown. Text-only first release, with tools disabled for both sides to keep side effects out of comparisons. Show this when entering comparison from a tool-enabled chat.

**Acceptance.** Identical input is delivered to each candidate. A quota for one remaining generation cannot admit two new calls. One provider timing out leaves the successful answer selectable. Refreshing after completion cannot trigger a second charge. Test cancellation, branch selection from two tabs, long code blocks and summaries of billed usage across all branches. ## D. Assistant presets that a project can share

**User journey.** From the chat menu choose **Save assistant setup**. Preview the model, instructions, enabled skills, allowed tools and collections. Exclude conversation text, attached files, local paths, credentials and permissions granted during the chat. Default to a personal draft. In **Extensions → Assistants**, a project editor can publish a version. A teammate selects **Use in chat**, sees what data the assistant can read and resolves any missing connection before sending. Show only the preset name in the composer, with details on demand. Slash commands keep their existing meaning for skills.

**Implementation.** Add a typed preset manifest, immutable versions and a scope to the existing catalog. Reference skill versions, collection IDs and explicitly allowed MCP tools. Apply organization policy and project constraints first, then the preset instructions within that scope. Keep retrieved text in the data channel. Bind credentials and device resources as the caller. Record the resolved version at run creation. For existing conversations show **Update available** with a diff. Restoring an earlier version creates a new revision. The test draft action uses a disposable chat scope. Common setup fields appear first, with resource bindings in a disclosure. Teltaq's agent editor shows model, instructions and tools together in a drawer. Our first screen needs only a name and a purpose to create a draft.

**Acceptance.** Two members can use the same preset with their own MCP identities. Import preview reports missing bindings individually. A newly requested tool appears in the version diff and never inherits the author's approval. Disabled models and removed project memberships have an actionable state. An active run keeps its resolved revision. [Teltaq agent templates](https://teltaq.com/blog/marketplace-agents-workflows) · [Agent editor screenshots](https://www.teltaq.com/screenshots)

## E. Test an assistant before sharing an update

**User journey.** In the preset editor, open **Test cases**, enter sample questions and specify expected text, source or tool behavior. Compare draft and current version. The summary leads with newly broken cases. Selecting a case shows the input, both answers, invoked tools and failed check. An optional manual rating captures why a change is acceptable. Keep this authoring surface out of ordinary chat.

**Implementation.** Store versioned datasets, cases, execution snapshots and results in the project. Run them through the same prompt assembly, retrieval and model adapter with an isolated run context. Use fixtures for all tools by default, including reads. Fixtures must represent empty results and errors. Never put eval runs into chat history or apply conversation approvals. Deterministic checks cover value, citation resolvability and expected/forbidden tool calls. Optional live model runs show planned call count and consume quota. An advisory model judge can follow once deterministic checks and human review are useful.

**Acceptance.** Seed a bilingual set covering “document has no answer”, “tool returned an error” and “model claimed completion without a successful tool result”. A deliberately broken fixture must expose the failing case and trace. Pin fixture and prompt versions, show partial/cancelled runs separately and do not score service failures as incorrect answers. Validate output redaction and access revocation. [Teltaq agent evaluation walkthrough](https://teltaq.com/blog/agent-evaluation-walkthrough) · [Retrieval evaluations](https://teltaq.com/blog/rag-evaluation)

## F. Turn a recurring task into a form with comparable results

**User journey.** In **Tasks → New**, choose **Weekly project brief**. A runner fills in period and audience, previews the bound project sources and presses **Run**. The editor has a separate view of three ordered steps: collect evidence, draft, review. The reviewer sees the draft and can accept or request changes. A completed task opens on its result, with **Compare with previous** and **Open conversation** nearby. Scheduling lives in the existing task editor. Project-scoped results are visible to members with read access. Personal task history remains private.

**Implementation.** First ship one preset with typed inputs (text, date, choice, project file) and a result artifact. Then add an ordered list of preset steps and an optional review checkpoint. Store a published definition version, run input snapshot, per-step attempt, upstream result and output digest. Start each report with an explicitly selected context so last week's answer cannot silently bias this week's research. Map typed inputs and previous outputs by field references. Save transitions in PostgreSQL and dispatch via the existing worker/outbox. Human review survives a worker restart. For an unknown side-effecting outcome, surface the affected step and require reconciliation before replay. Emit a private unread result through existing task indicators. Diff text by section and identify changes to source versions and report period.

**Acceptance.** Manual and scheduled execution use the same published definition. Two workers handling one weekly occurrence produce one result. A mid-run definition edit affects the next run. Review/reject, offline desktop, DST, result deletion, membership loss and “no previous result” all have distinct states. Two users cannot approve the same checkpoint twice. Pilot with one weekly report before considering parallel steps or a graph editor. [Teltaq form app walkthrough](https://teltaq.com/blog/agentic-apps-form-app) · [Scheduled results and activity](https://teltaq.com/blog/suites-complete-workspace)

## G. Answer questions over a CSV with inspectable numbers

**User journey.** From a project's CSV preview choose **Ask about this table**. Confirm column types, decimal separator and date interpretation. Ask “What were sales by region in October?” Each figure links to a small evidence table with metric, filter, date range, aggregation and dataset version. A number without a matching result is visibly marked. The reader can check which records contributed. This serves a different need from finding text in a document.

**Implementation.** First release supports bounded CSV snapshots. Parse in a worker with size, row and runtime ceilings, a preview and an explicit malformed-row policy. Persist typed rows in an isolated dataset namespace. The model proposes a structured query over permitted columns, filters, groups and aggregates. A server-side validator compiles it to parameterized operations. Give each output cell a stable reference. Bind numeric claims to those cells with unit, rounding rule and dimension. A match on magnitude alone cannot establish evidence. Query receipts open through the existing authenticated API. Record dataset version and query separately from generated prose.

**Acceptance.** Total, grouped sum and percentage change match known fixtures exactly within displayed precision. Tests include a decimal comma, duplicate labels, empty cells, mixed currencies, zero denominator, an ambiguous date and an unsupported metric. A changed or deleted dataset yields an explicit version state. No raw SQL, shell tool, spreadsheet formula execution or external connector is required. Advance beyond CSV only after a pilot user can independently reconstruct a reported number. [Teltaq data walkthrough](https://teltaq.com/blog/ask-your-data)

## H. Optional, explainable automatic model choice

**User journey.** Once an administrator enables a routing policy, **Auto** appears in the existing model picker. Its details show the candidate models, fallback and whether requests may leave the installation. On a reply, a small label identifies the actual model. Clicking it gives a short reason, including fallback or missing capability. Explicit selection remains sticky. Choosing a model for titles or the approval arbiter keeps its existing, separate setting.

**Implementation.** Start with ordered rules over enabled provider/model pairs, permitted destinations, tool support, input type, required context and an operator-selected fallback. Model capability metadata and implemented client/adapter support must both qualify. Unknown support does not satisfy a mandatory requirement. Validate that the fallback meets identical constraints. Add an optional classifier only after offline evaluation, with a short timeout and a routing-specific data policy. Send the minimum permitted text to a classifier. Record effective model, policy version, reason code, latency and usage. After the upstream call begins, a transport failure must not silently cause a second paid call.

**Acceptance.** Image input with no compatible adapter yields an actionable selection state. Local-only traffic stays within its configured destinations, including classifier and fallback. A timed-out router uses an eligible fallback once. Test against at least 50 labeled queries in EN/RU. Offer automatic selection only if it meets the operator's cost or latency improvement target without regressing required capability or fixture quality versus the fixed fallback. [Teltaq routing walkthrough](https://teltaq.com/blog/auto-model-routing)

## UX and release gates

- **Design the hard states first.** Prototype a citation to a deleted file, two competing model answers in a narrow window, and a tool waiting for a date while the user reads an older message. Then design the happy paths. Use the existing AIKit transcript for tool cards, Gravity UI Drawer for wide evidence panels, Sheet for narrow views and the existing task editor for step lists. Keep one primary action per state. Tool questions do not steal focus as they arrive.
- **Task-based validation.** Before public rollout, ask five representative users, including a project viewer and an author, to verify a quoted rule, answer a tool, select the better answer and find what changed in a weekly brief. Target at least four of five completing each unaided. Record the point of confusion and repeat that task after changes. These are proposed release targets, not measured results.
- **Interaction matrix.** Check web and packaged Electron, dark/light, EN/RU, keyboard and pointer, 390 px and wide layouts, 200% zoom, long localized labels, reduced motion, focus restoration and the desktop title-bar drag region. A citation opens with Enter, Escape returns to the same reference, and switching comparison tabs preserves each scroll position. Status uses text or icon as well as color.
- **Operational checks.** Add forward migrations and versioned contracts. Test an upgrade from the baseline, flag-off on existing chats, reconnect, concurrent requests and permissions revoked mid-run. Existing chats load without backfill. Disabling a feature prevents new work and preserves authorized history. Add per-feature latency/error counters in existing telemetry without prompts, excerpts, dataset rows or form answers. Collect usability timing on consented test sessions.

## What can wait

Cross-chat memory needs a separate decision about personal versus project ownership, consent and deletion. Publishing agents as inbound MCP endpoints introduces a new external access boundary that warrants a separate design. Mobile inference, local fine-tuning and a general workflow canvas have little bearing on verifying an answer, unblocking a tool or repeating a report. Revisit them when pilot teams can identify a recurring job the proposed milestones cannot complete.
