# UI и UX ZCode для развития Runóza

Runóza стоит перенять у ZCode прежде всего связный сценарий работы с кодом: видеть ход задачи, передавать точный контекст, проверять изменения и давать следующий запрос, не теряя текущую работу. Самая полезная часть — связь интерфейса с подтверждённым состоянием выполнения. Перенос визуальной библиотеки, всего рабочего стола или магазина плагинов для этого не нужен.

Основа сравнения: ZCode `a4b4445141eb7d3b3e99eada9292775383bfc44e`, Runóza `921cb0adbfaa7ca1e9e3b4340232c29d358bdd56`, 27 ноября 2026 года. Ниже рассматриваются исходники подключённых компонентов, их модели состояния и сценарии тестов. Это анализ реализации; приложение ZCode в рамках исследования не запускалось, визуальная точность и фактическая доступность его экранов не аттестованы. Наличие тестового файла не означает, что его проверки сейчас проходят.

Связанные документы: [техническое исследование агента](zcode-agent-engineering.md), [общий план внедрения](zcode-implementation-plan.md), [наши правила визуального развития](../design/visual-refresh-plan.md).

## Как устроен рабочий сценарий ZCode

В актуальной ветке UI основной узел разговора — `v4/SessionPane.tsx`. Он получает snapshot, строит status capsules, передаёт очередь в composer и отдельно показывает блокирующие взаимодействия. `ConversationTimeline` отвечает за длинную историю, `ConversationTurnGroup` — за содержимое хода и сводку файлов. Боковая панель объединяет файл, review, терминал, браузер и наблюдение за дополнительными агентами.

Это подключённые сценарии: `SessionPane` передаёт `snapshot.plan`, `backgroundWorks`, `workflowRuns`, состояния дочерних агентов и обработчики остановки в `ConversationStatusPanel`, а `snapshot.queue` — в `ConversationQueuePanel`. Детали возможностей проверяются до передачи обработчика: например, управление целью зависит от `availability`, отмена — от read-only/offline состояния. [Подключение status и queue](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/SessionPane.tsx#L6265-L6395).

Для Runóza полезно сохранить такую границу: сервер сообщает факты и доступные действия; компоненты выбирают представление. Клиентский spinner, локальный список задач или текст модели не должны становиться альтернативным источником статуса.

Это не календарные обещания. Для каждой идеи отдельно указан статус относительно Runóza: сохранить, расширить, добавить или отложить.

### UX-01 Видимый ход работы

ZCode показывает компактные элементы над composer: цель, план, Git и активность. В каждый момент открыт один popover; подписи сокращаются по доступной ширине. Модель отдельно определяет, существуют ли факты для отображения: отсутствие `nodesTotal` не превращается в выдуманные `0/0`, а отсутствие ручки отмены — в неработающую кнопку Stop. Порядок пунктов плана сохраняется при смене статуса. [Модель статуса](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/conversationStatusPanelModel.ts#L34-L205), [контейнер компактных статусов](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationStatusPanel.tsx#L94-L175).

В Runóza сначала достаточно существующих фактов: `Выполняется · 2 мин`, `Ждёт разрешения`, `Ожидает устройство`, `Сжимает контекст`. Нажатие открывает текущую операцию и переход к ней в истории. Показать место выполнения, когда оно помогает понять состояние, и отдельный Stop для запуска. Позднее сюда подключаются план и изменения; пустые элементы не занимают место.

Завершённые инструменты остаются в хронологии, но подробные input/output по умолчанию свёрнуты. Ошибка или запрос решения видны без раскрытия. Сводка не должна дублировать финальный ответ или скрывать `unknown` за общим «Выполнено».

**Точки изменения:** `RunActivity`, `ChatWorkspace`, `CodeActivity`, `ConversationHeader`; общая функция построения view model вместо нескольких независимых условий. **Приёмка:** live, reload и SSE reconnect дают одинаковое состояние; переход к операции не меняет порядок истории; сворачивание сохраняется во время стрима; событие ошибки видно при закрытых деталях. Screen reader получает объявление существенной смены состояния через отдельную live region; новые токены и каждое обновление таймера не озвучиваются. В первом этапе нельзя показывать проценты выполнения по числу токенов или времени.

### UX-02 План и режим планирования

У ZCode есть две разные поверхности: список пунктов `snapshot.plan` и просмотр плана, представленного через инструменты выхода из plan mode. Их нельзя смешивать в одну «галочку планирования»: список выполненных шагов описывает ход работы, а выбор режима влияет на разрешённое поведение агента. UI сохраняет исходный порядок пунктов, показывает состояния pending/inProgress/completed и открывает детали. [Пункты плана](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationStatusPanel.tsx#L521-L567), [подключение плана из snapshot](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/SessionPane.tsx#L6278-L6295).

Предлагается две последовательные поставки. Сначала — список плана в детали запуска: название, пункты со стабильными ID, текущий пункт, причина блокировки. Затем — явный вариант «Сначала составить план» с серверным ограничением mutating tools. Обычный запрос продолжает работать без обязательного многошагового плана.

Надпись «План готов» означает готовность документа плана, а не исполнение. Переход «Приступить» должен фиксировать выбранный план и фактические разрешения нового запуска. Read-only режим нельзя обеспечивать исключительно промптом или скрытой кнопкой в UI.

**Точки изменения:** `ChatWorkspace`, `RunActivity`, contracts/chat/agent; новый `RunPlan` как небольшой компонент. **Приёмка:** изменение статуса не переставляет строки; старые запуски без плана показываются нормально; после обновления страницы виден тот же план; планирование не выполняет запись/команды с побочным эффектом; одобрение плана само по себе не выдаёт полный доступ.

### UX-03 Понятное использование контекста

ZCode объединяет ёмкость окна, breakdown источников и часть информации о тарифных квотах. Важная деталь реализации: сегменты breakdown вычисляются по **числу символов** `chars`, а не по точному числу токенов; cache hit rate по умолчанию отображается лишь от 78%. Компонент не показывает невалидное/нулевое usage как достоверные 0%. [Расчёт и фильтры](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/chat-input-toolbar/contextUsage.tsx#L75-L237).

У Runóza уже есть `ConversationInfo` с контекстом последнего обращения и usage, `/compaction` и показ overflow. Полезное расширение — элемент `Контекст: около 42 тыс. / 128 тыс.` рядом с настройками composer, открывающий подробности: прошлое подтверждённое обращение, оценка следующего, резерв ответа, история, инструкции, вложения и схемы инструментов. Если доступен только общий размер, категории не выдумывать.

Каждое число должно иметь статус: provider reported, локальная оценка или недоступно. Если доли построены по символам, подписать их как относительный состав текста. Не скрывать низкий cache hit rate ради положительного впечатления; неизвестный показатель показывать как «Нет данных». Не смешивать стоимость, лимит тарифного плана и длину контекста в одном прогрессбаре.

Кнопка «Сжать контекст» использует существующий endpoint, а не новую локальную операцию. Состояния: доступно → запрошено после текущего шага → сжатие → готово/ошибка; сохранённая история остаётся доступной. После сжатия обновить оценки, сохранив дату/запуск, к которому относились прежние факты.

**Точки изменения:** `ConversationInfo`, `ChatWorkspace`, `RunActivity`, contracts usage. **Приёмка:** provider без usage, первый запуск, неизвестная ёмкость, смена модели, compaction во время работы и overflow имеют отдельные корректные состояния; накопленные токены всей беседы не выдаются за текущую занятость окна.

### UX-04 Точный контекст из рабочей области

ZCode различает вложение и ссылку на файл: drag из дерева в редактор вставляет mention, а не загружает файл заново. В composer также есть контекст выделенных фрагментов разговора, кода, web-элементов и других поверхностей. Комментарий к коду содержит путь, диапазон, выделенный текст и комментарий; текущая текстовая сериализация генерирует `Side: R`. [Drag и mention](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/prompt-editor/ChatPromptEditor.tsx#L285-L350), [модель комментария](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/lib/codeCommentContext.ts#L1-L155), [агрегация контекстов](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/composer/composerPromptContexts.ts#L1-L94).

В Runóza нужен узкий начальный набор: «Добавить файл в запрос» из `CodeWorkspace`, `@`-поиск по доступным файлам выбранного workspace и «Обсудить выделенный код». Чип показывает имя, строки и место выполнения; по нажатию открывает источник, по удалению исключает его из следующего запроса. Вложения S3, файлы проекта, виртуальные файлы беседы `runoza-files/…` и ссылки на workspace должны иметь различимые подписи, поскольку доступ и жизненный цикл у них разные. Виртуальный файл беседы не является путём операционной системы: он читается через `files_read/files_search`, а `files_export` отдельно копирует его в workspace с проверкой прав и конфликтов. Эти различия уже закреплены в [agent-files](../../packages/agent/src/agent-files.ts) и не должны исчезнуть в универсальном file picker.

Наш контракт лучше хранить структурно: `workspaceId`, `path`, `sha256`, `startLine`, `endLine`, `side`, `excerpt`, `comment`. Пара `side + revision` обязательна для diff; без неё комментарий может оказаться привязан к другой версии. Сериализованный текст для модели строит сервер. Ссылка не выдаёт ACL, а содержимое файла рассматривается как данные. При смене workspace устаревший чип требует повторного выбора; молчаливое переназначение запрещено.

Большие файлы включать через диапазон и существующие paged tools. Не помещать всё содержимое в prompt только из-за наличия mention. В MVP достаточно кнопки и компактного picker: переход на Lexical, как у ZCode, не является обязательным условием.

**Приёмка:** два файла с одинаковым именем в разных roots различимы; изменение хеша даёт «Источник изменился»; удалённый файл и потеря доступа не превращаются в пустой контекст; keyboard/IME/paste не ломают ввод; повторное открытие черновика сохраняет идентичность источника.

### UX-05 Проверка изменений после работы

`ConversationFileSummaryPanel` выводит число файлов, additions/deletions и загружает patch по раскрытию. Ключ кеша включает workspace/session/turn и состояние; во время исполнения и после завершения используются разные cache policy. Это позволяет не выдавать частичный diff за окончательный. Отдельный `GitPane` имеет источники изменений, включая last-turn, и ленивую загрузку diff; список виртуализирован. [Сводка файлов](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationFileSummaryPanel.tsx#L40-L195), [GitPane](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/GitPane.tsx#L1-L140).

В Runóza после code run показывать сводку «Изменено 4 файла» и действия «Посмотреть изменения», «Открыть файл», «Обсудить строки». В review явно разделять **изменения этого запуска** и **текущее состояние Git**. Несохранённые пользовательские правки и изменения другой работы не должны автоматически приписываться агенту.

Существующий `expectedHash` позволяет обнаружить несовпадение прочитанной и текущей версии, но сам по себе не гарантирует атомарность проверки и записи при произвольной конкуренции. Он также не хранит полноценный before/after audit и не обнаруживает все изменения shell-команд. Нужен серверный контракт изменений с исходной ревизией, конечной ревизией, типом изменения, источником, полнотой покрытия и ограничениями. Для бинарных/больших файлов показывать метаданные и причину отсутствия diff. Для команд с неопределённым исходом сохранять этот статус, а не рисовать зелёную сводку.

Начать с read-only review. Не добавлять рядом автоматические commit/push/merge до отдельного сценария полномочий. Выбор diff renderer делать после проверки больших файлов и доступности; наличие `@pierre/diffs` у ZCode само по себе не обосновывает новую зависимость Runóza.

**Точки изменения:** `CodeWorkspace`, `CodeActivity`, `MessageTranscript`; contracts/execution/agent/chat и хранение revisions. **Приёмка:** до запуска уже были правки, пользователь изменил файл после запуска, shell изменил бинарный файл, run остановлен, часть diff недоступна, workspace offline. При чтении старого run показывается сохранённая версия, а не случайный live diff.

### UX-06 Очередь следующих запросов

В ZCode очередь — проекция server/runtime state с собственными command handlers. UI умеет удалить и отредактировать пункт, изменить порядок, возобновить очередь и отправить пункт немедленно. Для редактирования запрашивается lock; интерфейс различает свой и чужой lock, подтверждённое и ожидающее состояние. `Send now` по контракту останавливает текущую работу и потребляет выбранный пункт. [Контракт и блокировки](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationQueuePanel.tsx#L36-L123).

Runóza сейчас сохраняет возможность писать в composer во время активного запуска, но обычное действие кнопки при активности — остановка. Стоит добавить явный выбор: «Добавить следующим» и отдельно «Остановить». Отправка во время работы должна создавать подтверждённый queue item, а не терять текст или неявно прерывать run. Пользователь видит место в очереди, краткий текст и статус принятия.

MVP: append, удалить, редактировать с revision/CAS, приостановить/возобновить автоматический запуск. DnD и «Выполнить сейчас» позже: сначала нужен проверенный протокол отмены. Кнопки изменения порядка должны работать с клавиатуры; drag не может быть единственным способом.

Каждый пункт фиксирует контекст, модель, target и необходимые extension references либо явно сообщает, какие настройки будут выбраны при старте. Live ACL и доступность модели повторно проверяются перед исполнением. Смена устройства или отзыв доступа переводят пункт в ожидающее/ошибочное состояние с понятным действием. После потери соединения показывать «Подтверждение не получено» и сверять по idempotency key.

**Точки изменения:** `ChatWorkspace`, conversation drafts, contracts/chat/db/worker. **Приёмка:** две вкладки редактируют один пункт, reload после отправки до ACK, disconnect/reconnect, duplicate click, отмена текущего run, потеря доступа и падение worker не создают двойной запуск и не теряют запрос.

### UX-07 Решение о разрешении в контексте задачи

ZCode переиспользует специализированные tool renderers для preview разрешения и показывает origin взаимодействия. Composer при блокирующей карточке сохраняется смонтированным, но скрывается визуально и из accessibility tree, чтобы не потерять черновик. Для сложного `SaveWorkflow` предусмотрена одна прокручиваемая область и закреплённые действия при достаточной высоте; это ограничение применяется именно к этому виду блока, не ко всем permission cards. [Composer при блокировке](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationComposer.tsx#L2906-L2938), [preview и адаптация карточки](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/PermissionDialog.tsx#L850-L944).

Для Runóza это развитие существующего `CodeActivity`: в первом экране показать действие, место, затрагиваемый ресурс, инициатора и срок/область разрешения. Технические аргументы — раскрываемая деталь. Рядом должны быть «Разрешить один раз», «Отклонить» и существующий выбор ограниченного сохранения правила. Полный доступ не превращать в более заметную кнопку, чем разовое решение.

Черновик и курсор сохраняются при появлении запроса. При выборе расширенного scope текст перед кнопкой должен отражать точную область; UI получает нормализованное правило от сервера. Несколько запросов показываются счётчиком и последовательностью, а не перетягивают фокус. `unknown` означает отсутствие подтверждённого результата и предлагает проверку состояния, не обычный retry.

**Приёмка:** длинная команда, длинный путь, mobile landscape, другой пользователь без права approve, истёкший запрос, повторный клик, отзыв разрешения и reconnect. Решение из устаревшей карточки не применяется к новой операции; фокус возвращается в прежнюю точку, а текст не пропадает.

### UX-08 Рабочая область рядом с разговором

ZCode использует боковую панель с типизированными вкладками. Терминалы имеют workspace identity и свой lifecycle; закрытие последней вкладки и закрытие конкретной сессии различаются. В широком UI можно менять ширину и открывать полный вид. Дерево файлов строится как виртуализированный `role="tree"`, поддерживает выбранный путь, Git state и обработчики клавиатуры. [Панель](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/app-shell/AnimatedSidePanePanel.tsx#L1-L137), [терминальная модель](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/terminal/terminalPanelState.ts#L1-L150), [список дерева](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/workspace-file-tree/WorkspaceFileTreeList.tsx#L112-L174).

Runóza уже имеет панель с файлами и терминалом, поэтому начать стоит с третьего раздела «Изменения» и единого открытия файла из результата агента. Запоминать выбранный файл, вкладку, раскрытые каталоги и положение панели по `org/user/conversation/workspace`. Смена разговора не должна показывать файл другого workspace. Сохранять только UI preferences и идентификаторы, не пользовательские prompts или содержимое файлов в localStorage.

На узком экране — один полноширинный workspace view с заметным возвратом в чат. Скрытие панели не завершает серверную работу или PTY; «Закрыть терминал» — отдельная операция с понятным последствием. Возможности сервера и desktop различаются по capability, без попытки открыть серверный путь в локальном Finder.

**Приёмка:** новый/существующий terminal, скрытие и возвращение, offline desktop, быстрые переключения бесед, dirty file, смена темы, resize и экранная клавиатура. Тяжёлые preview монтируются по необходимости; состояние вкладки переживает переключение без сохранения лишних активных renderer.

### UX-09 Адаптивный composer и дизайн

ZCode использует нейтральные поверхности, семантические `foreground/surface/border` tokens и компактную типографику; для dark/light заданы отдельные значения. `useComposerToolbarFit` измеряет реальную ширину и сворачивает подписи по приоритетам, учитывая смену языка и асинхронные controls. Измерение выполняется на невидимой inert-копии, чтобы не двигать живые кнопки и tooltip. [Токены](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/styles.css#L275-L328), [dark tokens](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/styles.css#L458-L501), [измерение composer](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/prompt-editor/useComposerToolbarFit.ts#L1-L132).

Эта логика согласуется с уже принятым направлением Runóza: нейтральный фон, читаемый текст, компактная навигация и Gravity UI. Сохраняем наш бренд, manta-активы, default dark и пользовательскую тему. Перенос Tailwind/shadcn/Radix или точных размеров ZCode создаст две системы компонентов без продуктовой пользы.

Composer должен сначала сохранять Send/Stop, место выполнения и доступ к настройкам; менее важные подписи уходят в компактное меню по заранее определённому порядку. Иконка без подписи получает доступное имя и tooltip, раскрытие остаётся возможно по tap. Подписи с текущим значением модели/режима не исчезают бесследно: они остаются в меню и summary. RU-строки и длинные названия моделей входят в исходные fixtures.

**Не переносить глобальное отключение фокуса.** В ZCode `styles.css` устанавливает `outline: none !important` и выключает focus `box-shadow`, включая forced-colors. Это не доказательство недоступности каждого отдельного контрола, но явный риск для компонентных focus styles и высокий контрастный режим. В Runóza сохранить видимый `focus-visible` на всех действиях, проверять Tab/Shift+Tab, Escape и возврат фокуса. [Глобальные правила фокуса](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/styles.css#L146-L178).

**Приёмка:** 390 px, desktop minimum, 1440 px; RU/EN × light/dark; длинное имя, несколько вложений, открытая боковая панель; IME и Enter/Shift+Enter; reduced motion, forced colors, 200% zoom. Ни одна обязательная кнопка не оказывается под draggable titlebar или за горизонтальным скроллом.

### UX-10 Длинный разговор без потери места

`ConversationTimeline` в ZCode виртуализирован, использует динамическое измерение высоты и отдельно обрабатывает пользовательское намерение уйти от нижнего края. История и текущий streaming turn разделены для сокращения повторной работы. Дополнительный `ConversationTurnNavigator` даёт навигацию по запросам и сам виртуализирован; на узкой области скрывается, а reduced motion учитывается при переходе. [Timeline](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationTimeline.tsx#L833-L890), [перехват намерения скролла](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationTimeline.tsx#L947-L1025), [навигатор](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationTurnNavigator.tsx#L33-L150).

Для Runóza сначала измерить длинные беседы на текущем AIKit renderer и существующих ограничениях истории. Затем отделить стабильные прошлые сообщения от активного, убрать лишние подписки и дублирующие загрузки. Виртуализация нужна, если измерения показывают проблему; копирование сложного timeline целиком не оправдано.

Контракт поведения: пользователь читает выше → новые токены не двигают viewport; кнопка «К новым сообщениям» возвращает follow; раскрытие tool details сохраняет якорь; подгрузка старой истории не сдвигает видимый текст. Навигация по шагам/запросам полезнее мини-карты без подписей: начать с доступного списка, затем решать, нужен ли постоянный rail.

В ZCode есть отдельные тестовые сценарии, измеряющие число geometry reads и render при прокрутке, а не только фиксированное время на случайной машине. Этот подход стоит перенять. [Сценарий производительности навигатора](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/test/browser/manual-review/pending/conversation-navigator-performance.test.mjs#L1-L115). **Приёмка:** 1000 сообщений и длинные tool outputs на синтетических данных; количество смонтированных строк ограничено при включённой виртуализации; typing и Stop остаются отзывчивыми; локальные измерения до/после приложены к изменению.

### UX-11 Расширения через конкретное действие

В деталях плагина ZCode показывает состав по типам MCP/skills/commands/agents/hooks, permissions и примеры запросов. Действие использования примера создаёт/подготавливает запрос с canonical reference, но не отправляет его автоматически. [PluginStoreDetailView](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/settings/PluginStoreDetailView.tsx#L65-L153).

Для Runóza достаточно улучшить уже имеющийся каталог: описание результата, один-два примера «Попробовать», scope, источник, версия, требования и доступность. Нажатие подставляет пример и включает конкретную доступную версию; пользователь проверяет текст и отправляет сам. Для MCP показывать «подключение есть, авторизация нужна» отдельно от «запрещено организацией» и «инструменты временно недоступны».

Глобальный marketplace UI, исполнение hooks и произвольные plugin UI не являются необходимой частью этой идеи. Skills и MCP сохраняют текущие разные модели доверия. **Приёмка:** пример не отправляется сам; обновлённая версия не меняет уже зафиксированный run; недоступный ресурс не предлагается как рабочий; effective scope виден без чтения технического JSON.

## Что отложить и что не копировать

### UX-12 Наблюдение за параллельной работой

В ZCode сводка активности открывает дочернюю сессию в панели наблюдения; `SessionPane` учитывает, что child tab не должен создавать composer и обещать продолжение, которого нет. Фоновые процессы и workflow имеют собственные control handles. [Наблюдение и доступные действия](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/SessionPane.tsx#L6271-L6339).

Для Runóza это следующий этап после ограниченного параллельного runtime: список «Исполнитель → задача → состояние → результат», открыть журнал, остановить конкретного исполнителя. Начать с read-only исследователей; не рисовать команду агентов поверх одного последовательного run. Стоимость, доступы, пути записи и последствия отмены должны быть решены технически до создания UI. Workflow-граф, анимированные лица, дизайнерский конструктор процессов и библиотека reusable workflows откладываются до появления подтверждённого спроса.

### UX-13 Возврат файлов

ZCode сначала получает preview rewind и разделяет safe/unsafe/ignored файлы, указывая причины: внешнее изменение, отсутствующий checkpoint, проигнорированный bash-эффект. Кнопка применения зависит от `canApply` и блокировки сессии. Это полезнее универсальной кнопки Undo с обещанием вернуть всё. [Rewind dialog](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/v4/ConversationFileRewindDialog.tsx#L26-L142).

В Runóza вводить такой UI можно только после сохранения before/after и проверки текущей версии прямо перед применением. Preview должен иметь ревизию/срок действительности; конкурентная запись инвалидирует его. Откат разговора, откат файлов и отмена внешних действий — разные операции. Сначала поставляем review, затем пилот rewind только для явно поддерживаемых файловых операций. Shell, внешние API, публикации и миграции не получают обещания универсальной отмены.

### Оболочка и визуальные эффекты

ZCode предлагает `office/coding` interface modes; office скрывает часть terminal/review launcher entries. Это полезная демонстрация progressive disclosure, но не модель прав. [Режимы](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/lib/interfaceMode.ts#L1-L9), [фильтрация панели](https://github.com/zai-org/ZCode/blob/a4b4445141eb7d3b3e99eada9292775383bfc44e/packages/ui/src/app-shell/AnimatedSidePanePanel.tsx#L795-L816).

В Runóza лучше показывать coding controls по доступным workspace capabilities и текущей работе, сохраняя обычный чат простым. Новый глобальный режим с обязательным onboarding не нужен для первой поставки. Копирование merchant quotas, конфетти при восстановлении лимитов, стеклянных поверхностей и WebGL-декора не решает задачи эффективного написания кода.

Не переносить монолитность крупных компонентов: в исследуемом снимке `ConversationComposer` содержит 3204 строки, `ConversationTimeline` — 2235, `ConversationStatusPanel` — 1672. Это размер файлов, а не оценка качества всего проекта, но хороший повод выделять наши view models, transport и небольшие renderer по ответственности с самого начала.

## Сквозной сценарий после внедрения

1. Пользователь выбирает проект и место выполнения; доступные возможности сразу видны. Из файла добавляет в запрос конкретный диапазон кода с зафиксированной версией.
2. При сложной задаче выбирает предварительный план. План появляется как документ и список шагов; согласие начать не расширяет существующие права.
3. Во время работы видит компактную строку статуса. Открывает текущий инструмент при необходимости; разрешение содержит ресурс, target и scope.
4. Пока агент работает, вводит следующий запрос и добавляет его в серверную очередь. Подтверждённый пункт появляется над composer; текущий run продолжается.
5. После завершения открывает сводку изменений, отличает изменения run от остальных правок в Git, комментирует точные строки diff.
6. Если контекст близок к лимиту, видит объяснимую оценку и запускает существующее сжатие. История, файлы и комментарии остаются доступными.
7. При уходе в другую беседу или повторном подключении возвращается к тому же состоянию работы, без дублирования команд и смешивания workspace.

Успех оценивается по конкретным сценариям: пользователь находит текущую операцию без поиска по всей истории; передаёт нужный диапазон без копирования пути вручную; проверяет изменения запуска; не теряет следующий запрос и черновик. Дополнительные продуктовые показатели — время до первого полезного действия, доля прерванных из-за непонятного состояния задач, число случайных остановок вместо отправки следующего запроса, время открытия review. Числовые цели задаются после baseline, а не заимствуются из чужого продукта.
