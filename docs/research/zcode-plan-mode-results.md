# Этап 5: сохраняемый план и режим планирования

Реализация в рабочем checkout, 27 ноября 2026 года. Продолжает этапы 0–4 и обзор изменений/контекстные ссылки этапа 6. Production не обновлялся.

## Поведение

В composer доступен выбор «Сначала составить план». Такой запуск исследует задачу разрешёнными структурированными инструментами чтения и сохраняет план через `plan_update`. План виден рядом с composer и в истории: версия, порядок шагов, текущий шаг, статусы и причины блокировки. Статусы плана не являются доказательством успешных тестов; результаты инструментов остаются в истории действий.

После завершения можно отредактировать план или нажать «Приступить». Правка создаёт новую версию с optimistic concurrency. Идентификаторы и взаимный порядок сохранённых шагов стабильны. Допускается не более одного шага в работе; заблокированному шагу нужна причина. После конфликта редактор сохраняет локальный текст и позволяет явно загрузить сохранённую версию.

«Приступить» создаёт отдельный code run с точной копией принятой версии. Сервер проверяет текущую ветку беседы, выбранную рабочую область, доступ, модель и обычные разрешения. Старую версию принять нельзя. Исполняемый план получает собственные версии прогресса; исходный план не переписывается. Перед изменениями агент должен заново проверить текущие файлы. Несохранённый черновик, вложения и ссылки на revisions не отправляются вместе с принятием плана и остаются в composer.

Обычные code runs также могут вести план для многошаговой задачи. Состояние загружается из базы, а worker передаёт текущий план в контекст после восстановления. Изменение плана учитывается при расчёте источника compaction context. Версия передаётся через SSE; обе UI-проекции используют общий query.

## Границы доступа

`intent=plan` — серверное ограничение возможностей запуска. Allowlist включает структурированное чтение workspace, bounded listing/search, чтение существующих виртуальных файлов и истории, чтение skills и cached MCP metadata, а также сохранение самого плана. Shell, записи файлов, экспорт/публикация, копирование skill resources, scratch-file mutations и внешние MCP вызовы/листинги запрещены. `readOnlyHint`, full access, remembered grants и human approval не расширяют этот список. Новые неизвестные инструменты запрещены по умолчанию.

Набор инструментов фильтруется при подготовке модели и повторно проверяется непосредственно перед dispatch. Permission service также отвергает запрещённые действия. План не отменяет существующие approvals на допустимое чтение. Подготовка среды, журналирование, архивирование больших результатов и сохранение плана — внутренние операции приложения; режим не является OS sandbox и не запрещает самостоятельные действия пользователя в терминале.

План и принятое выполнение привязаны к server conversation workspace либо конкретному desktop workspace. Подмена target отклоняется при admission, heartbeat и runtime authorization. Недоступное устройство не заменяется сервером. Повтор исходного planning request сохраняет потолок возможностей и target. Повтор принятого execution run через обычный retry требует нового запроса на планирование; это не скрытый replay действий.

API использует live read/write ACL. User edits запрещены, пока в беседе есть активный run. Runtime updates проверяют lease, статус и expectedVersion; повтор идентичного toolCallId идемпотентен. После отмены либо смены worker lease запись отклоняется.

## Хранение и выпуск

Миграция `040_run_plan` добавляет `intent`, `plan_version`, `plan_target`, `accepted_plan` в `chat_runs`, а также таблицу `run_plan_versions`. Существующие runs получают `intent=execute`, без плана и привязки нового типа. Старые request hashes без новых полей не меняются. Новых npm-зависимостей нет.

Перед выпуском использовать штатный migration runbook с backup. Откат 040 удаляет сохранённые планы и их acceptance metadata; нужен backup. Проверка выполнения не зависит от feature flag секционного prompt: legacy prompt получает обязательную инструкцию planning, а серверные ограничения работают независимо от prompt и structured-tools flag.
